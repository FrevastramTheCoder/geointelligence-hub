# Geospatial Capability Matrix

**Audit date:** 2026-10-10. Offline sample/metric/formula tests, local EE client API contract checks, planner routing checks and production frontend build pass. Live Earth Engine raster execution was not run in this audit because it requires a connected user's Earth Engine credentials, project and AOI.

## Execution architecture

1. `frontend/src/services/geoaiPlanner.js` maps natural-language aliases to a structured plan and contains a dataset registry.
2. `frontend/src/services/aiAssistant.js` handles conversation, follow-ups and planner output.
3. `frontend/src/components/assistant/AIAssistant.jsx` executes local tools, backend analyses, exports, zonal jobs and multi-step plans.
4. `frontend/src/services/geeService.js` posts structured requests to `/api/analyze`.
5. `backend/server.py` validates inputs, checks the account's Earth Engine connection, dispatches through `_run_analysis_impl`, stores jobs/results, and generates tiles/statistics/exports.
6. Local browser algorithms are in `frontend/src/analysis/`; local work does not imply a backend GIS engine.

## Runtime registry policy

- Planner registry entries must resolve to a real local handler, backend analysis ID, or dedicated API flow.
- Backend `IMPLEMENTED_ANALYSES` is the final analysis allow-list. A frontend alias alone is not proof of backend execution.
- Methodology-only records are returned as knowledge/requirements answers and must not be passed to `/api/analyze`.
- Add or change a capability only with its input contract, result type, limitations, and execution status.
